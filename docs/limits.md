# Status and limits

efforge is young, and the CLI's options may still change.

- Cloudflare is the only runtime.
- You can add add-ons but not remove them, and a single-choice slot only moves from `none` to a value. To switch from Postgres to D1, create a new project.
- Third-party add-ons aren't supported yet, and the add-on manifest format (`addon.json`) isn't stable.
- `efforge.jsonc` has a JSON Schema (`schemas/efforge.schema.json`, linked from the file's `$schema`). What is promised: `stack` and its values mean what the schema says, and a newer efforge reads an `efforge.jsonc` written by an older one. What isn't: the `files` hashes are internal and may change format, and new fields may appear.
- The `--json` output is versioned (`contract` in every document, see [json.md](json.md)): within one contract version, fields and error codes keep their names and meanings. The text output for people may change at any time.
- `infra=alchemy` uses Alchemy 2.0 beta (`2.0.0-beta.87`). Drizzle is pinned to the `1.0.0-rc.5` release candidate ([why](decisions/0002-drizzle-rc-pin.md)).
- Generated projects pin every Effect package to one version with `overrides` in `pnpm-workspace.yaml` ([why](decisions/0005-effect-lockstep-overrides.md)). The wildcard entries need pnpm 12.17 or later; the project's `packageManager` field pins 12.21.0, and pnpm switches to it on its own. When you upgrade `effect`, change the catalog entry and the overrides together. The `effect` entry only covers Effect 4, so a library that depends on Effect 3 (uploadthing, Prisma) keeps its own copy. The family wildcards are not scoped that way: `@effect/ai-google`, `@effect/sql-drizzle` and `@effect/sql-kysely` have no Effect 4 release, so they can't be installed alongside the overrides.
- A project made by efforge 0.2.0 has no overrides and pins pnpm 12.4.2, so it can install two Effect versions and fail `pnpm build` with `failed to resolve import "effect/..."`. `upgrade` repairs it, and so does any `efforge add` from 0.2.1; [Keep a project current](upgrading.md#without-the-new-cli) has the repair by hand.
- With `infra=alchemy`, local settings live in `.env` (`alchemy dev` reads it) instead of `.dev.vars`; efforge writes them there at `create` and at every `add`. On D1, `pnpm dev` and `pnpm run deploy` apply the migrations; `pnpm db:migrate` needs a `wrangler.jsonc` and says so.
- CI generates, installs and runs the full gate (typecheck, check, test, build) for a matrix of 20 stacks (the three presets among them), not every combination. Between them they build every add-on on every database it allows (`test/matrix-coverage.test.ts`).
- With `--auth=none`, the `effect-ai-byok` demo server function is not gated, so anyone who can reach the app can spend the configured API key. Add auth or remove the demo before deploying.
- With `--auth=none`, the database, storage, workflows and email cards' server functions are not gated either: anyone who can reach the app can add notes, upload to and delete from the bucket's `uploads/` folder, start and watch workflow runs, and, with `MAIL_TRANSPORT=cloudflare`, send a test email from your domain to any address. Every card that writes or spends says so. Add auth or remove the demos before deploying.
- With `--auth=none` the realtime room has no access check: anyone who can reach the app can join a room, read what is sent and send to it. The realtime card says so. With auth, the upgrade needs a session, but a socket that is already open stays open after its user signs out, until it closes.
- On auth stacks, "requires a session" means any account, and sign-up is open: anyone can register (no verified email needed) and then use every card, including the ones that spend your AI key, send the test email from your domain and drive the browser container. Close sign-up with Better Auth's `emailAndPassword: { enabled: true, disableSignUp: true }` in `apps/web/src/server/auth.ts`, or remove those demos, before you deploy with real keys. Within the app, uploads and workflow runs are per user (with organizations too, not per organization); notes are shared by every user on purpose.
- On auth stacks, `sessionGate` (global function middleware in `apps/web/src/start.ts`) refuses every server function without a session at runtime, except those in `apps/web/src/server/public-server-fns.json`, matched by the file and name TanStack Start's compiler records. It covers server functions however they are written (an alias, a re-export, a wrapper). `requireApiSession`, first in `workerRoutes`, refuses every request under `/api/` without a session, except `/api/auth/`, whether a Worker route or a route file's `server: { handlers }` answers it. Not covered: a Worker route or route-file handler outside `/api/` (the realtime socket and the signed `/files/` links check for themselves), and a project that removes either line or edits `start.ts` so `functionMiddleware` is no longer passed to `createStart`. The lint rule `efforge/server-fn-session` is early feedback only: it sees `createServerFn` imported from `@tanstack/react-start` and called in the same file, and reports it aliased or re-exported.
- Server functions and the socket upgrade don't check `Origin`. What stops a cross-site request carrying a user's cookie is the session cookie's `SameSite=Lax` and the browser's CORS preflight for JSON bodies; TanStack Start's CSRF middleware is not on.
- The build check that keeps server files and secrets out of the browser looks for whole-file imports and for the values of settings named like secrets (`*SECRET*`, `*KEY*`, `*TOKEN*`, `*PASSWORD*`, 8 characters or more) in `.dev.vars` and `.env*`. A secret kept elsewhere, or under another name, is not checked.
- `extras/cluster` is experimental, as `@effect/platform-cloudflare` is upstream: its API may change in a patch release, so efforge pins it exactly, with `effect`. In 4.1.4 a durable sleep that is the first thing a workflow run awaits wakes about a minute late (two alarms race; [cluster.md](cluster.md#what-experimental-means-here)), nothing runs a queue worker in the background (the request that offers runs it, for up to 10 seconds; no Cron Trigger is wired), and `pnpm dev` must be restarted after a handler changes. Its deploy, on wrangler or Alchemy, and everything that only shows on real Durable Objects (eviction, hibernation, several isolates, alarm timing, code updates while an entity is kept alive) are not tested. Counters and review runs are per user with auth; the greeting queue is shared.

## Not in 0.3.0

- No `observability` add-on. Every service call and server function is already a named span, and `TelemetryLive` in `layers.ts` is the slot for a tracer, but Effect's Cloudflare tracer is merged upstream and not yet in a published `@effect/platform-cloudflare` (4.1.4 has none). The add-on waits for that release.

## Never verified

- Nothing efforge's tests run deploys to a real Cloudflare account. CI builds every stack; the furthest any test goes is `pnpm run deploy --dry-run` on upgraded wrangler projects, which builds the Worker and checks its config. Alchemy stacks are built, never planned against an account. A first deploy, the `prod` stage on Alchemy, Hyperdrive in front of a real Postgres, and the R2, email, container and Durable Object bindings in production are the parts the docs describe but no test has run.
- The browser add-on's container is built and its card refuses local and private addresses, but it has not been run against a public page on the machine that tested this release.
- `extras/cluster`, beyond what is above: its deploy, and anything that only shows on real Durable Objects.
